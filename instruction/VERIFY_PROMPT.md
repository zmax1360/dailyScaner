# Verification Prompt

Paste into a **fresh** Claude Code session — fresh matters, because an agent that wrote the
code will defend it. Run this after each step, or after any session where an agent touched
`attribution.py`, `best_value.py`, `config.py`, `dailyScaner.py`, `mark_runner.py`, or
`health_check.py`.

---

## The prompt

```
You are auditing an attribution logging layer in this repo. Assume it is broken until
proven otherwise. Your job is to find where it silently fails, not to confirm it works.

Do not trust comments, docstrings, variable names, or any prior session's claims about
what is implemented. Read the code and RUN it.

For each check below: state PASS or FAIL, and paste the command output that proves it.
"Looks correct" is not an answer. If you cannot run something, say so explicitly and mark
it UNVERIFIED — never infer a PASS from reading.

=== A. Completeness of the record ===

A1. Does log_run write EVERY scored contract, or only a top-N slice? Find any limit,
    head(), nlargest(), or truncation between calculate_best_value and the INSERT.
    Prove it: run a scan, then compare runs.n_scored against COUNT(*) in flags for
    that run_id. They must reconcile exactly (flags = n_scored + control rows).
    Note (not a FAIL by itself): the scorer universe may be archive head(30)/side —
    that is pre-score. Post-score truncation is a FAIL.

A2. Is the multiplier breakdown complete and auditable from the DB alone?
    Each non-control flags row MUST persist nlev, nflow, base_score, and multipliers.
    Take one flags row and prove:
      score_from_flag_parts(nlev, nflow, multipliers, base_score=base_score)
        == score   (to 1e-9 after round(4))
    Also: every multiplier applied in best_value.py via _apply must be recordable in
    the JSON when it fires. Missing nlev/nflow/base_score on the latest run is a FAIL.
    Helper: attribution.score_from_flag_parts / test_db_row_multipliers_reproduce_score.

A3. Are control rows generated by rule and independent of engine output? Show the
    selection code. If selection depends on Value_Score or is drawn from the scored
    set as its selection method, that is a FAIL. (ATM may overlap scored strikes —
    that is OK if the rule is chain+spot+expiry only.)

=== B. Immutability ===

B1. Can a flag row's score, rank, multipliers, mid, nlev, nflow, or base_score ever be
    UPDATEd after insert? grep every UPDATE and DELETE against flags. Anything touching
    a decision field is a FAIL. mark_* updates are allowed only with AND mark_* IS NULL.

B2. Can a mark be overwritten? Write a mark, attempt to write a different value to the
    same row/horizon, read it back. It must be unchanged.

B3. Run the marker twice in a row. SUM of each mark column must be byte-identical.

=== C. Silent failure modes ===

C1. What happens if the scan runs and logging raises?
    Required: scan continues AND an alert is attempted (alert_attribution_failure /
    Telegram). Scan dies = FAIL. Continues with print-only and no alert = FAIL.

C2. What happens if fetch_option_mid returns a stale or zero price? Trace it. If a 0.0
    can be written as a mark, that is a FAIL — a zero mark is indistinguishable from a
    contract that expired worthless, and it will silently poison ret_t1d.
    write_mark must refuse <= 0; failed fetch must return None.

C3. Is config_hash actually derived from the values used in scoring, or from a dict
    that could drift out of sync with the literals? Change one multiplier in config.py,
    confirm the hash changes AND that the score changes. If the hash moves but the score
    doesn't, the config is decorative.

C4. Are timestamps ET-aware everywhere in the logging or marking path? grep for
    datetime.now() without a tz, and for date.today(). Any naive datetime in
    attribution.py / mark_runner.py / health_check.py / log_run ts path is a FAIL.

=== D. The experiment is still valid ===

D1. How many distinct config_hash values exist in the last 30 days? More than one means
    the sample is contaminated — report which runs used which.
    engine v1 fingerprint (record if changed): see config_hash(SCORING).

D2. Does the rank column reflect the FINAL post-multiplier ranking, or the pre-multiplier
    order? Verify by sorting flags by rank and checking score is nonincreasing.

D3. Are there scored contracts with score IS NULL and is_control = 0? That means rows
    are being logged without a verdict. Report the count.

D4. Latest run: COUNT of non-control rows with nlev/nflow/base_score IS NULL must be 0.

=== E. Report ===

Produce a table: check | PASS/FAIL/UNVERIFIED | evidence.
Then list, in severity order, every way this logger could produce a confident but wrong
answer in six weeks. Be specific about which query would be misleading and why.

Do not fix anything. Report only.
```

## Why it's shaped this way

**"Assume it is broken."** An agent asked "does this work?" will find reasons it works. Asked
to find failures, it finds failures. Same model, different prior.

**"Do not trust prior sessions' claims."** You've been burned by AI rewrites that silently
reverted a strategy while reporting success. A fresh session with an adversarial frame is the
cheapest defense.

**A2 is the load-bearing check.** Non-empty multipliers JSON is not enough. The product of
`base_score × ∏ multipliers` must equal stored `score` using **only columns on the flags
row** — no chain replay. That is why `nlev` / `nflow` / `base_score` are persisted.

**C1 is the ops twin of A2.** A scan that continues without an alert can drop an entire
trading day of rows while Telegram Best Value still looks healthy.

**C2 is the one that would cost you the month.** A zero mark and a worthless expiry look
identical in the data. If `fetch_option_mid` can return `0.0` on a failed fetch, your
`avg_ret` quietly drifts toward −100% and you'll conclude the engine is terrible. Confirm it
returns `None` and the row stays NULL.

**D1 catches the subtle one.** If you retune a multiplier mid-experiment and pool the results,
you're averaging two different engines and the answer is meaningless in a way that produces a
perfectly plausible-looking number.

## Quick daily version

For a fast check between full audits:

```bash
python health_check.py
# or raw SQL:
```

```sql
-- against data/attribution.db
SELECT 'today', COUNT(*) FROM flags WHERE date(ts_et) = date('now','localtime');
SELECT 'empty_mults', COUNT(*) FROM flags WHERE multipliers = '{}' OR multipliers IS NULL;
SELECT 'overdue_t1h', COUNT(*) FROM flags
  WHERE mark_t1h IS NULL AND ts_et < datetime('now','localtime','-4 hours');
SELECT 'hashes_7d', COUNT(DISTINCT config_hash) FROM runs WHERE ts_et > date('now','-7 days');
SELECT 'zero_marks', COUNT(*) FROM flags WHERE mark_t1h = 0 OR mark_t1d = 0;
SELECT 'null_score', COUNT(*) FROM flags WHERE score IS NULL AND is_control = 0;
SELECT 'latest_missing_base', COUNT(*) FROM flags
  WHERE run_id = (SELECT run_id FROM runs ORDER BY ts_et DESC LIMIT 1)
    AND is_control = 0
    AND (nlev IS NULL OR nflow IS NULL OR base_score IS NULL);
```

Expected: today > 0 on a trading day; empty_mults / overdue / zero_marks / null_score /
latest_missing_base = 0; hashes_7d = 1.

For anything off, find the cause before writing more rows — every bad row makes the
eventual analysis harder to trust.

**Pasteable A2 one-liner (latest run):**

```bash
python -c "
from attribution import _db, score_from_flag_parts
with _db() as c:
    rid = c.execute('SELECT run_id FROM runs ORDER BY ts_et DESC LIMIT 1').fetchone()[0]
    rows = c.execute(
        'SELECT score,nlev,nflow,base_score,multipliers FROM flags '
        'WHERE run_id=? AND is_control=0', (rid,)
    ).fetchall()
mism = sum(
    1 for r in rows
    if abs(score_from_flag_parts(r['nlev'], r['nflow'], r['multipliers'],
                                 base_score=r['base_score']) - r['score']) > 1e-9
)
print(rid[:8], 'n=', len(rows), 'mismatches=', mism)
"
```
